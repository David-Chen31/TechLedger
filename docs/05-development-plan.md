## 2. 计划中的仓库结构与模块边界

当前目录只有需求文档，尚无应用源码，也不是 Git 仓库。编码阶段建议使用一个仓库管理网页、API、worker 和文档；具体目录在第一阶段落地时确定。模块应保持以下边界：

- **Web**：来源与运行状态、决策卡审查、历史与评测；通过 API 操作，不直连数据库或模型。
- **API**：输入校验、权限边界（MVP 单用户）、资源查询、任务创建、事件流；不在请求线程完成整次调研。
- **Source/Index worker**：批准来源获取、解析、快照、关键词/向量索引、删除一致性检查。
- **Research runtime**：流程状态、模型调用、证据组织、引用校验和预算。
- **Decision service**：人工批准、修订、退回、来源变化标记与复核历史。
- **Evaluation harness**：冻结数据集、基线运行、逐例评分、报告导出；与产品运行使用相同来源快照和核心检索逻辑。

跨模块数据传递须有清晰 schema 和版本；不要用一个通用字典承载全部来源、运行和决策数据。外部工具和来源连接器应能被模拟，CI 不依赖真实网页和付费模型。

## 3. 交付节奏（目标 6 周，允许 4–8 周调整）

| 阶段 | 核心产物 | 通过门槛 | 主要风险 |
|---|---|---|---|
| G0：需求与数据锁定 | 审核后的 PRD、来源审查表、首批页面快照、题集 v1、模型预算 | 至少 2 个可使用的官方来源族；5 道校准题可人工核查；正式题集与评分规则有版本 | 来源许可或可用性不满足 |
| G1：工程骨架与来源闭环 | Git、前后端基础、数据库迁移、Compose、来源登记/同步/解析 | 一条命令启动；导入、失败、重试及快照不可变均可演示 | 开发环境与网页解析不稳定 |
| G2：检索与证据 | 关键词基线、向量索引、引用定位、来源清理 | 同一快照可重建索引；引用能打开到正确章节；删除无孤儿索引 | 混合检索收益不明显 |
| G3：调研与决策闭环 | 有界研究流程、REST/SSE、决策草稿、人工批准与修订 | 正常、无证据、冲突、超时、取消均有明确状态；未批准草稿不可作为知识检索 | 模型产生无据主张 |
| G4：来源更新闭环 | 手动同步、差异元数据、受影响决策标记、人工复核 | 受控 5 个更新例均能追踪到相关卡片；无关卡片误报单列 | 页面微小改动导致过多提醒 |
| G5：评测与展示 | B0/B1/B2 对照、逐例日志、失败分析、用户审查、README 与演示脚本 | 报告公开所有任务与口径；CI 不调用付费模型；演示含一次成功、一次失败、一次来源更新 | 时间不足或用户审查者缺席 |

若只能投入 4 周，优先完成 G0–G3 和最小来源更新示例；明确推迟向量检索或用户实验，并如实缩小简历主张。若有 8 周，优先修复评测暴露的质量问题，不自动扩展到通用平台。

## 4. 每阶段交付证据

每阶段结束至少提供：改动清单、架构或接口变更、启动/测试命令与真实结果、一个正常用例、一个失败用例、尚未解决的风险。G2 起保存固定任务输入与输出，G5 公开逐例运行 ID、来源版本和指标计算脚本/表。任何性能数字在测量前都不能写进 README 或简历。

测试重点按风险安排：来源解析与快照哈希、引用存在性、状态转换、未批准内容隔离、模型超时/限流、SSE 重连、索引删除、来源变化标记、提示注入与密钥泄漏。端到端至少覆盖“导入→提问→审查→批准→来源更新→复核”。测试使用固定快照和模拟模型，真实模型只用于单独的演示与正式评测。

## 5. 开工检查表

进入编码前确认：

1. 用户认可 `PRD.md` 的新产品方向与 MVP 边界。
2. 首个技术领域和来源清单确定，来源登记表完成可用性与引用方式审查。
3. 至少 5 道校准题和评分样例可人工核查；正式题集的采集计划明确。
4. 真实模型服务、单任务预算和演示机器条件有记录；没有付费密钥也能通过模拟流程跑测试。
5. DevFlow-Agent 与 TechLedger 各自的演示任务、数据集和简历证据分开维护。

本清单是避免方向与数据反复变动的准备工作。已确认的事项不用反复向用户索取许可；实施中的小型技术取舍可按 PRD 自主决定并记录。
