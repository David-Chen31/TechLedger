# TechLedger 产品定位与用户研究准备

状态：开发前草案｜2026-10-28｜主需求以仓库根目录 `PRD.md` 为准

## 1. 名称与产品承诺

**TechLedger（技术决策账本）**：Ledger 强调决策、来源和复核历史可追踪。对外副标题使用“让技术选型有证据、能复核”。仓库目录目前仍叫 AgentStudio；用户界面、文档标题和演示脚本统一使用 TechLedger，避免出现两个产品名。

产品承诺限定为三件事：给出可核查的技术主张；明确与团队约束有关的取舍；来源变化时提醒用户复核。系统不承诺自动替代架构师，也不把模型生成的建议自动发布为团队结论。

## 2. 用户任务与场景边界

| 角色 | 触发事件 | 现在的做法与成本 | TechLedger 应提供的结果 |
|---|---|---|---|
| AI 应用工程师 | 项目要选择 Agent 编排或知识检索方案 | 打开多个官方文档、release notes 和旧调研，手动核对版本，容易漏掉限制条件 | 有来源日期和约束匹配说明的决策草稿 |
| 技术负责人 | 审核组件选型 | 反复追问“证据在哪、何时有效、为什么排除 B” | 可逐项审查的决策卡，含未知项和反对证据 |
| 新成员 | 接手已有技术方案 | 只看到结论，不知道当时依据 | 历史决策、批准人/时间、来源快照和后续复核记录 |

**首个窄场景**：为 Python Agent 服务选择编排框架。候选来源以 LangGraph 和 CrewAI 的官方文档及官方发布记录作为起点；它们是数据准备候选，不预设比较结果。正式纳入前要核查可访问性、引用限制、发布时间和可获得的历史版本。首版只回答这一领域的问题，例如：在明确部署方式、可恢复性、团队学习成本和人工审查需求后，如何比较两种方案。

官方来源入口：[LangGraph 文档](https://docs.langchain.com/oss/python/langgraph/overview)、[LangGraph Releases](https://github.com/langchain-ai/langgraph/releases)、[CrewAI 文档](https://docs.crewai.com/en/introduction)、[CrewAI Releases](https://github.com/crewAIInc/crewAI/releases)。具体页面和版本将在数据集冻结时记录，不能在评测运行过程中随意切换。

## 3. 产品假设与反证

| 假设 | 最低成本验证 | 失败信号 |
|---|---|---|
| 用户愿意复用带来源的技术决策卡 | 请 3 位有研发经验的人完成同一选型审查，观察他们是否实际打开证据并愿意保留决策卡 | 只看结论，仍需从头搜索，或认为卡片比直接读文档更慢 |
| 来源变化提醒有实际价值 | 选取已批准卡片，模拟其引用文档的可控更新，观察用户能否迅速判断需不需要改结论 | 大量无关变化产生提醒，用户普遍忽略 |
| Agent 多步核验优于单轮总结 | 用冻结题集比较单轮基线和完整流程的主张正确率、冲突发现、成本与耗时 | 准确率无提升，成本与延迟显著增加 |

如果第二、三项失败，应缩减为证据检索与人工决策记录工具，不因“Agent”名称保留无收益的多步流程。

## 4. 待访谈问题

访谈对象：至少 3 位做过 AI 应用组件选型或维护的工程师。先让受访者讲最近一次真实选型，避免只问“你想不想要这个产品”。

1. 最近一次选择框架/组件是什么？谁提出，谁批准，最终结论存在哪里？
2. 查证时最费时间的三件事是什么？哪些资料最常过时或互相矛盾？
3. 决策必须考虑哪些硬约束？哪些只是偏好？
4. 旧结论通常由谁维护？什么变化会触发重新评估？
5. 请用一份示例决策卡完成审查：哪条主张你会打开来源核对？哪里还缺证据？
6. 如果不给自动推荐，只给证据对照和更新提醒，你还会使用吗？为什么？

记录原话、任务、耗时和行为；不要把礼貌性“有用”回答当作验证。受访者不能招募时，在展示材料中写明用户价值尚待验证。

## 5. 首版用户流程与成功定义

用户选择技术主题 → 输入问题与硬约束 → 查看来源范围 → 启动调研 → 审查每条主张和出处 → 修改/批准决策卡 → 来源重新同步时复核受影响结论。

一次任务“成功”须同时满足：结果覆盖用户给定硬约束；关键事实有可定位且版本匹配的出处；冲突与未知项没有被掩盖；用户能独立做出批准、修改或退回判断。模型给出一个听起来合理的推荐，不构成成功。

## 6. 与 DevFlow-Agent 的演示区隔

DevFlow 演示的是“公开 Issue → 复现 → 修改 → 测试 → 修复包”，技术焦点是工具执行与安全边界。TechLedger 演示的是“技术问题 → 多来源证据 → 人工批准的决策 → 来源更新后的复核”，技术焦点是知识新鲜度、引用真实性、冲突处理和决策生命周期。两个项目的 README、数据集和简历主张分别建立。

## 7. 当前未定但不阻碍准备的事项

- 演示领域最终是否固定为 Agent 编排框架；若改领域，仍需保持 2–3 类批准来源的窄范围。
- 使用哪个模型服务、单任务费用上限和本地机器配置。
- 能否招募 3 位真实审查者。
- 官方来源的内容抓取、索引与展示许可；不允许时应使用元数据和链接，不强行保存全文。

这些事项要在开发计划的第一道门槛前冻结，并写入评测数据版本。
