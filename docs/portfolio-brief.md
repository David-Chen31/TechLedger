# TechLedger 项目展示提纲

**一句话**：为小型研发团队的技术选型保留可核查的证据、人工批准记录和来源变化后的复核提醒。首个演示范围限定为 Python Agent 编排框架。它处理的是技术资料与决策知识；DevFlow-Agent 处理 Issue、代码定位和补丁，两者任务不同。

## 面试时的 90 秒介绍

技术选型讨论常依赖口头印象，数周后很难回答“当时依据是什么、资料更新后结论是否需要复核”。我做了一个本地单用户原型：审核官方来源的使用范围后建立快照与索引，用有限查询规划检索候选方案的证据，生成待审核决策卡。用户可以回到原文、修订或退回，来源索引变化会标记已批准卡片待复核。后端 FastAPI/PostgreSQL/worker，前端 Next.js；Docker Compose 一键运行，REST 与 SSE 传递任务状态。

我没有把模型输出直接标成可信事实：程序只把逐字可核对的来源摘录记作已核验证据，摘要交给审核。为了验证查询规划，冻结两份来源和六道新题后，以同一 BM25、相同片段截取和证据上限做对照。能力规划的模型输入片段覆盖率为 75%，旧规划为 0%，但两道题仍漏证据；这是小样本检索结果，不能推断真实决策质量。三次真实 DeepSeek Flash 调用的草稿审核与 Token 用量另有记录。

## 后续优先级

优先扩大独立题集和真实开发者访谈，验证是否真的节省决策复核时间。随后用新的题集验证来源内 top-k 与跨候选证据配额；只有语义检索在同条件下确实提升覆盖，才加入 embedding 和向量库。当前不把多 Agent 角色数或低代码画布当成产品价值证明。
