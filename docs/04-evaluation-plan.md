# TechLedger 评测设计与结果发布规范

状态：开发前草案｜2026-10-28｜评测任务尚未采集，本文不包含实测成绩

## 1. 要回答的三个问题

1. 与简单检索加单轮总结相比，多步核验是否让事实和引用更可靠？
2. 决策卡是否真正遵守用户约束，并清楚暴露冲突与未知项？
3. 当资料发生变化，系统能否准确指出需要复核的决策，同时控制无关提醒？

如果完整流程只增加成本和延迟，没有质量收益，报告必须如实呈现，并将产品收敛为检索与人工决策记录工具。评测先于实现冻结能力定义，避免以演示结果反推成功标准。参照 [Anthropic 的 Agent 评测实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) 制定逐例任务和失败分析。

## 2. 数据集结构

| 子集 | 最低规模 | 来源与标注 | 主要用途 |
|---|---:|---|---|
| 事实/版本核查 | 20 题 | 人工从已批准的官方文档与发布记录提炼；每题标出正确来源快照、章节、答案和时间范围 | 事实正确性、引用有效性、版本意识 |
| 技术选型 | 10 题 | 对同一领域设置不同硬约束，如可恢复性、人工审查、部署限制、成本边界；人工定义必须核查的维度，不预设唯一正确框架 | 约束遵守、比较完整度、未知项处理 |
| 来源冲突 | 至少 5 例 | 真实来源冲突优先；若不足，使用明确标注的受控冲突样例，单独报告 | 冲突识别与语气控制 |
| 来源更新 | 至少 5 例 | 保留旧快照和受控新快照，标注哪些卡片引用了变化来源 | 需复核提示与误报 |
| 失败/边界 | 至少 5 例 | 无日期、无证据、来源不可用、模型超时、提示注入等 | 稳定性、拒答和错误状态 |

一题可属于多个子集，但汇总时分别列分母。每题保存 `case_id`、问题、硬约束、允许来源快照、标注者、核查点、预期证据、答案接受范围、排除理由、创建时间和数据版本。正式测试集在第一次正式运行前冻结；调整必须生成新版本并保留旧结果。

### 数据泄漏控制

- 模型输入只包含当次允许的来源快照；人工标准答案和评分规则不进入检索索引。
- 版本变化题用旧快照作初始状态，再同步新快照，不让新材料提前进入旧运行。
- 如直接使用公开文档生成题目，不能假设模型从未见过文档。因此评测主张是“系统对指定快照的核查与可追溯性”，不是模型泛化能力。
- 调参用例与最终展示用例分开记录；不能反复挑选表现最好的 10 题作为正式结果。

## 3. 对照方案与运行条件

| 方案 | 内容 | 目的 |
|---|---|---|
| B0：关键词 + 单轮 | 同一批准来源与快照中进行关键词检索，将有限片段交给同一模型一次生成 | 最低工程复杂度基线 |
| B1：关键词 + 向量 | 在相同内容预算内混合召回，一次生成 | 测检索改进的独立收益 |
| B2：完整 TechLedger | B1 加问题拆解、主张核验、冲突处理与决策卡审查前校验 | 测多步流程的收益与代价 |

若 B1 未实施，仍需比较 B0 与完整流程，但明确无法单独归因向量检索收益。各方案尽量使用同一模型、温度、来源快照、输入问题和接近的上下文预算；差异全部记录。每题至少运行 3 次，报告每次结果以及汇总的均值/范围，不只保留最佳输出。

## 4. 指标与评分规则

| 指标 | 计算口径 | 评分方式 |
|---|---|---|
| 事实正确率 | 正确且限定到正确来源版本的关键事实数 / 所有人工核查关键事实数 | 两名标注者按来源核对；分歧记录后裁决 |
| 引用结构有效率 | URL、快照、章节/范围均可定位的引用数 / 所有输出引用数 | 程序校验；无引用的关键事实另计无据主张 |
| 引用语义支持率 | 引用内容确实支持对应主张的引用数 / 抽检引用数 | 人工按“支持/部分支持/不支持”标注；主报告以严格支持计数 |
| 约束遵守率 | 无违反硬约束的选型题数 / 10 个选型题 | 标注每项硬约束是否被识别、满足或明确说明无法满足 |
| 冲突识别率 | 明确展示两方证据与版本的冲突例数 / 冲突例总数 | 人工核查；只写“可能有分歧”不算识别 |
| 更新提示召回率 | 被标记需复核的受影响卡片数 / 所有受影响卡片数 | 根据受控更新映射计算 |
| 提醒噪声率 | 被标记需复核、但人工判断所引主张无需重新评估的卡片数 / 所有被标记卡片数 | 区分来源内容变化、主张证据变化与结论变化；逐例说明原因 |
| 未经支持的确定性主张数 | 无足够证据仍以事实口吻写出的关键主张数 | 人工计数，列出逐例原文与原因 |
| 运行代价 | 端到端 P50/P95、Token、估算费用和失败率 | 以所有运行作为分母；失败/超时单列，不静默剔除 |

技术选型题的建议不强制与标注者完全相同；能否满足硬约束、权衡是否有证据、未知项是否透明，比“选择 A 还是 B”更重要。人工评分表按每一维 0/1/2 分：缺失或错误、部分满足、充分且有证据；报告给出评分说明和分歧数。

## 5. 工程验收目标与产品价值判断

**必须通过的工程门槛**：无不存在的来源/快照引用；程序可核对每个引用范围；受控 5 例来源更新均触发相应需复核状态；用户未批准的草稿不会进入决策检索；运行失败、取消、超时的状态与原始轨迹可查。这些要求不依赖模型表现，应由自动化测试覆盖。

**待实测的质量目标**：引用语义支持率至少 90%，10 道选型题中至少 8 道不违反硬约束，完整流程的事实正确率或冲突识别率高于 B0。目标若未达到，仍保留原始结果与失败分析；经需求复核后决定是否迭代或缩小场景，不改写结果。

**小规模用户审查**：至少邀请 3 位有技术选型经验的开发者，分别审查同一批材料的 B0 输出与 TechLedger 决策卡，记录核查用时、被发现的误导性主张、打开来源的次数、是否愿意存档及原因。顺序交叉安排，说明样本小、只支持方向性结论。无法招募时，不声称已经验证用户价值。

## 6. 失败分类与报告结构

失败至少分成：来源不可用、解析/索引错误、检索遗漏、资料过时、引用不支持主张、来源冲突未发现、用户约束误解、模型格式错误、预算/超时、人工审查退回。一个任务可有多个原因，需标记主因。

公开报告顺序：数据集与来源版本 → 配置和预算 → 基线定义 → 全部逐例结果 → 指标汇总 → 成本/时延 → 典型成功与失败 → 用户审查观察 → 适用边界。结果表和原始记录保留稳定的任务 ID 与计算口径；简历数字必须能回到相应结果文件。未获允许的原文不直接打包公开。
